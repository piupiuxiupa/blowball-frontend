## Context

本地后端 `api/openapi.yaml` 已明确以下行为，前端根目录的契约已同步：

- 空闲与排队发送均返回 `200 text/event-stream`。排队流先发 `queued`，然后等待；执行开始后，同一条流继续发送 `agent_start` 等事件。
- `queued.meta.run_id` / 响应头标识未来执行的 run，`queue_position` 只是入队时的参考位置。`queued` 没有 `agent`，不是消息历史行。
- `GET /sessions/{session_id}/queue` 返回 FIFO 等待列表；队列项包含 `run_id`、原始 `content`、已解析模型、入队时间及可选图片引用。等待用户行直到开始执行才进入消息历史。
- 会话列表和详情在等待数大于零且队列开启时携带 `queued_count`；字段省略既可能是空队列，也可能是能力关闭。
- 队列满返回 `409 QUEUE_FULL`，没有必须提供的 `run_id`。队列关闭时保留 `409 SESSION_BUSY` 与当前 run id。
- 现有 cancel 端点既能取消活跃 run，也能移除 queued run；取消当前 run 不影响其他等待项，撤回与 pump 竞争时可能返回 `queued`，不能据此宣布撤回成功。

当前 `useSendMessage` 的 mutation 一直等待整个 SSE 消费结束；输入区把 `turnActive`、mutation pending、上传和建会话合并为 `busy`。发送响应头直接覆盖 `turnRuns[sessionId]`，错误路径回滚整个历史快照并清流，游标按会话保存，均不适合并发提交等待消息。消息列表把历史块放在实时段之前，不能直接把等待用户消息追加进历史。已有 `StreamingSegment.runId` 表示子 Agent 的 dispatch 身份，不能改成顶层队列 run 的含义。

## Goals / Non-Goals

**Goals:**
- 运行中保持可编辑并继续提交；发送、停止当前 run、撤回某个等待项各有明确目标。
- 用真正的 SSE 入队确认和服务端队列读模型恢复等待状态，不构造客户端调度器。
- 保留每会话至多一个活跃输出订阅，同时连续衔接后端 FIFO 执行；run 身份、游标和收尾互不污染。
- 保持图片、模型、上下文、草稿创建、历史导航和子 Agent 的现有能力。

**Non-Goals:**
- 不修改后端队列开关、深度或调度实现；不增加客户端硬编码队列上限。
- 不支持编辑、重排、批量清空等待项，也不做浏览器本地持久化队列。
- 不迁移同一新版契约新增的 staged 图片上传端点，不替换现有会话内上传流程。
- 不引入新的生产依赖，不归档或改写本次变更之外的现有工作区修改。

## Decisions

### D1：分离编辑、提交确认和执行生命周期

输入区分别维护按会话归属的提交状态、活跃 run 与取消目标。只有建会话、上传和等待当前提交确认时锁定对应发送动作；运行/attach 本身不锁定正文、模型与附件。停止入口单独显示，只读取已确认的活跃 run；其「停止中」状态绑定目标 run id，不能等全局 busy 变 false 才复位，否则连续执行会把下一轮停止按钮一直锁住。

发送捕获正文、序列化上下文、图片文件及引用、模型和思考等级快照。优先在服务端接受后清空匹配的输入快照，而不是无条件清空再全局恢复；会话切换或草稿修订后，旧请求结果不能清空/覆盖新的正文、上下文或图片。成功上传的图片仍复用已有按会话缓存，错误不要求重新上传。

备选「只删除 busy 中的 turnActive」会留下长 mutation、共享 abort controller 和错误回滚的竞态，不采用。

### D2：queued 确认后 detach，运行输出由独立生命周期持有

新发送路径读取首个有效事件，区分排队与立即执行：

```text
提交快照 ── POST /messages ── 首个有效 SSE
                             ├─ queued：确认接受，展示等待项，detach 等待连接
                             │           └─ GET queue / session 探测后续执行
                             └─ 执行事件：登记 active run，将后续事件交给独立消费者
                                         └─ done → 历史收尾 → 再探测 active run
```

- `queued` 用 meta run id、再以响应头兜底标识等待项；不能把该头直接写成当前 active run。处理必须位于活跃 run 兜底登记和分段写入之前。
- 入队已确认后主动断开只表示 detach，不取消服务端等待项，也不走请求失败恢复或当前 run 的清流逻辑。
- 立即执行路径把已经读取的首帧及剩余迭代器交给长期运行消费者，不能重新解析已被读取/锁定的 response body，也不能丢失首个 `agent_start`。
- mutation 表示提交确认而不是等待整轮结束；输出消费与组件内 mutation 实例解耦，由按 run 的生命周期注册表持有控制器与收尾。
- 首帧判断仅用于新提交分类。对会话详情已证明 `generating: true` 的 active run 进行 attach 时，重放的 `queued` 是日志前缀：忽略其展示输出，继续等待/消费 `agent_start`，不得再次 detach。

备选「保留每个排队 POST 的长 SSE，等它自行开始」协议上可行，但会长期占用多个等待连接并增加多个消费者同时修改会话状态的风险。选择 detach + 服务端读模型探测，延续现有单活跃输出订阅的架构。

### D3：独立队列读模型和输入区上方的待处理展示

新增队列查询 hook，缓存键为 `['session-queue', sessionId]`，通过既有 API base 读取队列（后端路由确认属于 api 分区）；POST 消息、attach 和 cancel 继续走 agent base。所有路径编码 session/run id 并保持现有鉴权。草稿哨兵不发队列或会话详情请求。

等待项按服务端顺序和 run id 去重；新入队确认可先显示一个临时确认项，随后由队列快照接管。`queued_count` 省略按零显示，但不作为能力开关；实际队列列表由队列读取提供，`queue_position` 不成为永久序号。

在输入区上方增加紧凑、可折叠的待处理区，展示内容预览、解析后的上下文 chips、图片引用、已知模型与入队时间，逐项提供「撤回」操作；图片沿用会话附件 content URL，不渲染模型占位文本。等待项不进入 `messages` 缓存、`groupMessages`、用户历史导航或划词引用的 turn 编号。队列消失只改变等待展示，实际开始/完成由 active run 和消息历史接管，避免重复用户气泡。

备选「把 optimistic user message 直接 append 到 messages」会使等待消息排到当前流式回复之前并污染回合与导航，拒绝。

### D4：有界探测和连续 run 衔接

活动会话打开/聚焦时读取队列及详情；入队、撤回和本地 run 终局后立即失效该会话的 queue/detail/messages 与必要的列表缓存。存在本地活跃输出、服务端 generating、等待列表或刚确认的等待项时，对当前可见真实会话做约 1.5 秒的有界周期探测；空闲且无等待项后停止，不对所有隐藏会话持续轮询。

run 发现继续采用「列表缓存快路径、详情权威裁决」。active run 改变/旧订阅释放也触发重新评估，而不是只等待切换或聚焦；若详情的新 candidate 曾被旧订阅阻挡，旧 run 收尾后必须再检查。若下一轮已经快速执行完毕，重拉历史同样能够展示结果，不要求一定看到它的实时阶段。

不能仅因一条队列项从列表消失就把它认作成功执行或取消，也不能清除当前流。契约允许队列读取故障降级成空 200，前端无法从该快照区分真实空队列与故障；后续探测恢复展示，不将其当作 run 终局证明。

### D5：顶层 run 身份与条件清理

长期订阅、游标和错误/终局回调携带固定 `(sessionId, turnRunId)`。`Last-Event-ID` 按这对身份保存；新 run 不能使用前一轮的游标。会话流式段仍复用已有存储结构，但增加独立的顶层 owner 判据；保留段上的子 Agent `runId` / `agentInstanceId` 原义。

reconcile、fallback 和 finally 只能释放自己拥有的 run、控制器与流式分段。A 已结束、B 已接管时，A 的迟到重拉/取消/错误回调不能清 B 的登记或输出。入队请求的失败也不能执行整会话历史快照回滚或 `clearStreamingSegments`。普通立即执行的乐观用户行按提交/run 身份清理或对齐，不能退回一份包含过时历史的快照。

### D6：撤回与停止观察不同的取消结果

停止当前 run 维持「发 cancel、继续消费当前流、确认部分输出落库」行为；等待区撤回以等待项的 run id 发同一端点，但必须观察返回值，不能复用当前吞掉结果的 `Promise<void>` 包装来宣布成功。

`cancelled` 才能显示明确撤回成功；`queued` / `running` / `cancelling` 保持处理中并刷新 queue/detail，针对同一 run 做有限次数重试或提示稍后再试。已终局 `done/error/interrupted` 表示等待项已不是可撤回状态，刷新并显示实际情况，不伪称撤回成功。取消请求失败保留等待项并显示错误；当前 run 与其他队列项不受影响。

### D7：兼容关闭队列和请求错误

前端不在发送前根据缺失的计数猜测能力关闭；服务端确认 `SESSION_BUSY` 时保留未发送快照，静默 attach/去重当前 run，并用非弹窗提示说明本条尚未发送。`QUEUE_FULL` 显示可重试原因而不清流、不自动 attach、不假定固定容量。模型/思考等级、图片、大小、鉴权和网络错误继续按请求边界处理。

收到接受证据后，网络中断是订阅问题，不能自动重新 POST 或当作未接受进行重复发送；用 queue/detail/history 和现有 attach 重连恢复。尚未确认的连接异常也不自动重试 POST，以免后端已接收但回执丢失造成重复排队。

## Risks / Trade-offs

- [detach 后看到下一轮有探测延迟] → 入队/取消/终局立即刷新，等待阶段有界短周期探测；历史覆盖已经快速完成的轮次。
- [attach 重放 queued 被当作再次等待而断开] → 新提交分类与已知 active run 消费分开，并增加重放前缀回归测试。
- [旧 run 收尾与新 run 接管交错] → 固定 run owner、条件清理、按 run 游标和「旧订阅释放」的重新发现触发。
- [停止中状态在连续轮次不复位] → 绑定取消目标 run id，目标终局/active 身份变化即复位，而非依赖全局 busy。
- [队列空 200 无法区分读故障，展示可能短暂缺失] → 不据此宣布完成/撤回，不影响当前 SSE，并在后续探测恢复；这需要后端未来提供诊断字段才能彻底区分。
- [跨会话或新草稿被旧请求回调覆盖] → 结果只作用于原始 session 和匹配修订快照，避免整个消息缓存回滚。
- [现有图片/子 Agent 改动未提交] → 实现以当前工作区为基线，生成类型后逐项检查兼容，不能还原现有功能改动。
- [仓库缺少现成 test script] → 优先抽离 SSE 分类、队列对齐与 run owner 的纯逻辑，用已有 Node/TypeScript 能力加入最小回归入口；不增加生产依赖。

## Migration Plan

1. 契约已经与本地后端文件同步；实现阶段运行现有 `generate-api`，确认新增队列类型与 staged 端点只是契约增量，不迁移图片流程。
2. 先完成提交/订阅生命周期拆分和 run 身份隔离，再接队列查询、撤回与输入区展示，保留旧的 `SESSION_BUSY` 兼容。
3. 覆盖 queue 开/关、满队列、刷新、撤回竞态、连续运行、跨会话及图片/上下文的自动化与浏览器回归，再运行类型检查和构建。
4. 部署方确认后端队列开启；前端无数据库或配置迁移。回滚前端会失去等待消息入口与展示，但后端已入队消息仍按服务端语义运行，不能通过前端回滚删除队列。

## Open Questions

- 目标环境是否已经开启 `messages.queue.enabled`？不阻碍前端实现，但联调需覆盖开启和关闭两种部署行为。
- 后端是否计划为队列读取的降级空响应增加诊断标记？本次仅按已有契约做恢复，不能凭空判定真实终局。
